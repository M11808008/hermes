RAG 準確率如何從 60% 提升到 85%：面試題拆解與工程檢核

一句話摘要

RAG 的品質通常不是靠「換一個更大的模型」單點解決，而是要把資料切分、查詢理解、召回／排序、流量路由與評估指標拆開量測，逐層找出錯誤來源。

影片主張的改善路徑

### 1. 先修正資料切分，不要只用固定字數一刀切

影片用「每 500 個 token 固定切斷」作為反例，指出句子、段落、表格可能被切開，導致檢索命中的是殘缺內容。它建議依 NLP 边界／標題／段落做動態切分，並保留約 100–200 token 的重疊窗口，讓相鄰片段保留上下文連續性。

實務上，重疊不是越大越好：它會增加索引量、重複召回與成本。應用固定評估集比較 chunk size、overlap、語意邊界與表格／程式碼特殊處理，而不是直接採用影片的數字。

### 2. Query rewriting 後要做語意護欄

對「怎麼退款？」這類短而含糊的問題，影片建議先用小模型擴寫或產生多個查詢，再進行檢索。但它特別提醒：改寫模型可能把「怎麼退款」誤改成「怎麼賺錢」，所以要用 embedding 相似度或其他語意檢查，比對原問題與改寫問題；低於門檻就捨棄或回退原問題。

這個想法的重點不是固定 0.8 這個門檻，而是建立 query rewrite 的可觀測性：保存原始 query、改寫結果、採用／拒絕原因、召回差異與最終答案品質。

### 3. 混合檢索不能直接把不同量綱的分數相加

影片指出向量檢索分數與 BM25 關鍵字分數的量綱不同，直接用 `向量分數 + BM25 分數` 可能讓其中一種分數完全壓過另一種。畫面與旁白提到要先做分數融合／統一排序，再搭配 reranker；影片 ASR 對相關英文名稱不穩定，畫面可辨識的概念是混合檢索與排序模型，而非某個已核實的特定模型名稱。

Elastic 的 Reciprocal Rank Fusion（RRF）文件提供了一種以排名融合多個 retriever 結果的正式做法；它與影片「不要直接相加」的工程提醒方向一致，但不代表 RRF 在所有資料集都會勝出。

### 4. 用策略路由平衡品質、延遲與成本

影片以 reranker 約需 200 毫秒、併發上升後系統壓力變大作為示例，建議簡單問題走較快的向量檢索，複雜問題才啟用 reranking。這是一種 query／流量路由策略，不是「所有請求都加上最重的模型」。

導入時應記錄：問題類型、是否啟用 reranker、top-k、端到端延遲、token／API 成本、答案品質與失敗率，並以離線資料集加線上抽樣確認路由沒有把困難問題誤判成簡單問題。

### 5. 把「答案不好」拆成 retrieval 與 generation 問題

影片最後提醒，不要只看一個總體準確率：

  • Context Recall：必要答案是否出現在取回的 context 中；若不在，優先查 retrieval。
  • Faithfulness／groundedness：答案是否忠於取回資料；若資料有答案但模型答錯或添加未支持內容，優先查 generation／提示與引用約束。
  • Answer relevance：答案是否真的回應使用者問題。

Ragas 的指標文件、LangChain 的 retrieval 架構文件與相關 RAG 工具鏈都支持把檢索和生成分層觀察的方向；實際指標定義與評估方法仍需依資料集校準。

影片重點流程

  • 文件解析與語意／結構化切分。
  • 建立帶有適度 overlap 的索引。
  • 對短 query 做受控的 query rewriting 或多路查詢。
  • 使用向量檢索與關鍵字檢索取得候選。
  • 以 RRF 等排名融合方法或 reranker 統一排序。
  • 依問題難度做策略路由，控制延遲與成本。
  • 分開量測 context recall、faithfulness、answer relevance、延遲與失敗率。
  • 以錯誤案例回饋 chunk、query、retriever、reranker 與 generator 的下一輪調整。
