Facebook｜ChatGPT 連接 GitHub：查詢專案、程式修改與分支隔離工作流

一句話摘要

這則貼文把 ChatGPT 與 GitHub 串接成網站維護入口：先指定 repository，再讓 AI 讀取專案、提出或執行修改，並以 branch／pull request 降低直接碰觸主線的風險。

Facebook 貼文重點

作者陳盟升公開分享的操作描述如下：

  • 在 ChatGPT 左上方的外掛程式區域選擇 GitHub。
  • 綁定 GitHub 後，在對話框左下角的加號選取專案。
  • 告訴 GPT 要處理哪個 repository，讓它查詢專案內容。
  • 需要時要求 AI 修改網站或程式。
  • 貼文稱系統會建立分支，避免直接影響主線。
  • 作者以自己放在 GitHub 上的網站作為使用情境。

貼文圖片中可辨識到 ChatGPT 的工具呼叫紀錄與約 3 分 48 秒的處理時間；圖片解析度不足，無法可靠逐字抄錄完整 prompt 或確認畫面上的正式產品名稱。

還原後的實作流程

  • 先確認 repository、目前 branch 與目標工作範圍。
  • 讓 ChatGPT／Codex 先讀取 README、專案結構與相關檔案。
  • 先要求提出修改計畫與影響範圍，不要一開始就直接改 main。
  • 在獨立 branch 執行修改，或讓 Codex 以 pull request 為交付單位。
  • 執行測試、建置與網站預覽檢查。
  • 人工檢視 diff、權限變更、環境變數與部署設定。
  • 通過檢查後才合併 pull request，並確認 GitHub Pages 或其他部署結果。

官方查核與需要校準的地方

OpenAI 的 GitHub Codex 文件目前可讀取，頁面標題為「Review GitHub pull requests with Codex」。文件描述 Codex 會檢視 pull request diff、遵循 repository guidance，並發佈標準 GitHub code review；這支持「ChatGPT／Codex 可進入 GitHub 工程工作流」的大方向。

但這不等於下列說法已被官方文件普遍保證：

  • ChatGPT 的所有方案都能直接修改任意 GitHub repository。
  • 所有帳號介面都仍叫「外掛程式」，或都在左下角加號提供相同 GitHub 選擇器。
  • 每次操作都會自動建立 branch。
  • GitHub 連接操作一定不消耗 Codex 額度。
  • AI 產出的修改可以不經人工 review 直接部署。

較精準的理解是：GitHub connector、Codex 任務、pull request review 與 repository 權限可能是不同能力層；可用功能取決於產品介面、帳號方案、組織政策、OAuth scope 與 repository 權限。貼文的「不佔 Codex 額度」保留為作者的使用心得，未視為通用規則。

對 GitHub Pages 網站的安全用法

  • 先使用 preview branch，不直接在 main 上試錯。
  • 把 API key、token、學生資料與私密設定留在 GitHub Secrets 或伺服器端，不能交給前端 bundle。
  • 要求 AI 只修改明確列出的檔案，避免無意間改動部署 workflow。
  • 合併前檢查 diff、連結、圖片、HTML／JavaScript 錯誤與 mobile layout。
  • 若 repository 具有自動部署，任何 merge 都可能觸發公開發布，需先確認 Actions 與環境變數。
  • 將 ChatGPT 的建議視為 draft；權限、刪除檔案、付款、發佈與資料外洩相關操作必須保留人工批准。

對 AI 學習雷達的價值

這則分享的重點不只是「把 ChatGPT 接上 GitHub」，而是把網站維護從單次問答改成可追蹤的工程流程：AI 讀取 repository，分支承接修改，pull request 留下 diff 與審查紀錄，再由人決定是否合併。對教學網站、GitHub Pages 與個人作品集尤其實用。

可用一句話記住：

ChatGPT 讀 repo → branch 隔離修改 → pull request 審查 → 測試 → 人工合併 → 自動部署
