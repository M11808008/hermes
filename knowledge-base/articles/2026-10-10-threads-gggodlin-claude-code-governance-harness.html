Threads｜gggodlin Claude Code Harness：把 Agent 治理做成「人做決策、機制負責觸發」的可拆式參考架構

一句話摘要

這個專案的核心不是讓 Agent 無人值守地「自我進化」，而是把 **人類該做的決策保留給人，把提醒、阻擋、稽核與例行觸發交給機制**。

社群貼文說了什麼

作者 gggodlin 在 Threads 公開其個人 Claude Code harness／治理架構，貼文列出約 40 支 hooks、40 個 skills、22 個 commands、20 個 subagent 定義與 13 份常駐規則，另外還有 memory、wiki 等多套機制。作者同時給出重要但書：這些內容高度反映個人工作習慣，**不建議整套複製**，應交由自己的 Agent 閱讀後再挑選適合的部分導入。

貼文中的「決策歸使用者，觸發用機制」是這份架構最值得帶走的原則；數量則以貼文發布時的作者自述為準，不應當作長期固定規格。

官方 repository 可確認的內容

GitHub repository `GGGODLIN/gggodlin-cc-harness` 將自己定位為個人 Claude Code harness 的治理層，包含：

  • `CLAUDE.md`、`rules/`、output styles 與引用資料等常駐規則。
  • 由 `settings.json` 註冊的 hooks，將部分規則從「模型自行遵守」改為機械化檢查。
  • 支援規劃、實作、審查與查證工作流的 skills、commands 與 agents。
  • memory、wiki、trial（新機制觀察期）、friction（摩擦事件）等制度；公開版僅放虛構範例，不含作者的私人內容。
  • `compact-guard`，用於在 context 壓縮前保留可稽核 checkpoint，並提供 Codex 支援。

README 也確認它是 **reference，不是產品**：部分私人接線被移除、路徑與工具設定依原作者環境而寫；即使可個別安裝，整套也不保證在其他人的機器可直接運作。

為什麼這種治理比「多塞規則」更重要

一份很長的規則檔，並不等於 Agent 會遵守。這個專案的有效思路是把要求分層：

  • **人決定範圍與風險**：例如是否發布、是否刪除、是否動到重要設定。
  • **規則說明標準**：什麼情況要查證、何時停下來問、怎樣算有證據。
  • **hooks 強制關鍵節點**：對能程式化判斷的事情，改由機制提醒或攔下。
  • **觀察期與摩擦紀錄回饋設計**：新工具先記錄真實使用情況，再決定保留、調整或移除。

其中「完成宣稱要帶證據」尤其適合用在 Agent 工作流：如果 Agent 說已完成、已測試或已部署，就要求同時提供實際指令與輸出；無法提出時，應縮小宣稱範圍。

不能忽略的導入風險

README 已公開列出多個不可照抄的高風險點，這是本專案值得肯定也必須認真對待的部分：

  • 部分指令會暫改 `~/.codex/config.toml`、強制移除 git worktree，若中斷或環境不同，可能覆蓋設定或刪除未提交檔案。
  • 有些流程會下載、安裝或執行第三方套件；評估工具本身不等於零副作用。
  • 某些自動 closeout 規則可能自動 commit、push；以路徑判斷工作／個人 repository 的設計，搬到別人的目錄結構可能誤判。
  • 排程與本機分析腳本含環境相依的路徑與未公開元件；README 明說必須自行補接線。
  • repo 雖主要採 MIT，但 `THIRD_PARTY_NOTICES.md` 指出其中有上游授權內容，且 `skills/mutation-testing` 含 Business Source License 1.1，不應把所有檔案一概視為 MIT。

因此，這不是「複製貼上到 `~/.claude`」就該執行的套件。任何 hooks、shell 腳本、排程、可修改設定或可 push 的 commands，都應逐檔審閱、移除私人路徑與高權限動作，並先在測試帳號、測試 repository 與隔離目錄驗證。

建議的最小導入路徑

  • 先讀 `README.md` 的設計原則與已知風險，不安裝任何元件。
  • 從單一、可還原的元件開始；作者推薦可先研究有完整程式與測試的 `compact-guard`。
  • 將「證據化完成宣稱」與「新工具觀察期」兩個原則，先以你現有工具重做，而非直接搬移作者檔案。
  • 針對每一支 hook 建立：觸發事件、讀寫檔案、會執行的命令、失敗行為與回復方式的清單。
  • 在非重要 repository 跑一段觀察期，量測 token、時間、中斷率、誤擋率與人工注意力成本，再決定是否擴大。

授權與維護界線

repository 的自寫內容採 MIT；然而公開版本會由作者的私人來源重新產生，因此不接受 pull request，因為下次匯出會覆蓋。若要貢獻，README 指示以 issue 描述改進建議。使用前也應針對引入的上游檔案個別檢查 `THIRD_PARTY_NOTICES.md`。
