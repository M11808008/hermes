Threads｜three.js 純程式生成場景：先用 layout.js 鎖定空間，再談鏡頭與 70 秒影片

一句話摘要

把 AI 交付的三維影片拆成「可驗證的空間規格 → 程式化資產 → 光照與鏡頭 → 離線輸出」：第一步不是畫面，而是一份所有模組都必須服從的 `layout.js`。

原始 prompt 的核心

Austin（@ai_cpocoder）提出一個 three.js 場景任務：以程式生成一座黃昏時刻的日本寺廟，最終輸出 70 秒影片；禁止 3D 模型、貼圖與照片，主殿、五重塔、拱橋、蓮花池、山門都要由程式生成。

其中最值得複用的限制是：**先不寫畫面，先寫 `layout.js`，以公尺定義每個建築的位置與大小；之後所有程式只能從這一份讀取座標。** 光照則事先鎖定為西南西、地平線上方約 7 度的暖色太陽。

這是處理 agentic coding 的好方法。當場景生成、植物、鏡頭、碰撞、特效和輸出分別由不同模組或不同 agent 負責時，若每一段都自己猜座標，成品幾乎必然出現比例不一、建築互撞、鏡頭穿模或重構成本暴增。`layout.js` 相當於場景的 API 契約。

可直接重用的任務提示

以下是保留原始意圖、但補上工程驗收條件的版本：

```text

你是 three.js 技術美術與前端 3D 工程師。

目標：以 three.js 製作一座黃昏時刻的程序化日式寺廟場景，供最終 70 秒離線影片渲染使用。

硬性限制：

  • 不使用任何外部 3D 模型、照片或貼圖；所有建築、地面、水面、植被、材質細節均以幾何、顏色、shader／程式邏輯生成。
  • 第一個交付物只能是 layout.js；此階段不可建立 renderer、模型、動畫或相機。
  • layout.js 是唯一座標真相來源。所有後續模組只能 import 它，禁止散落的 magic numbers。
  • 單位一律為公尺，Y 軸向上；座標原點定義為山門中心地面。

layout.js 必須輸出：

  • 場景邊界與地形高度規則；
  • 主殿、五重塔、拱橋、蓮花池、山門的 position、rotation、width/depth/height 與安全間距；
  • 主步道與鏡頭可通行區；
  • 太陽方位：西南西；太陽高度：7 度；暖色光參數；
  • 鏡頭起點／終點候選點，但不要寫動畫；
  • validateLayout()：檢查物件邊界、建築間距、橋梁與池面關係、鏡頭路徑是否穿過實體。

請先回傳：

A. 空間配置的文字說明；

B. 完整 layout.js；

C. validateLayout() 的檢查清單與預期輸出；

D. 尚未做的項目清單（渲染、材質、資產、動畫、影片輸出）。

```

layout.js 的最小結構

不必一開始就追求精確建築考據；先建立可維護的資料結構。示意如下：

```js

export const METERS = 1;

export const scene = {

bounds: { minX: -55, maxX: 55, minZ: -45, maxZ: 65 },

groundY: 0,

sun: {

azimuthDeg: 247.5, // 西南西，以北為 0° 的專案慣例

altitudeDeg: 7,

color: '#ffb36b',

intensity: 2.2,

},

};

export const landmarks = {

gate: { position: [0, 0, -33], size: [9, 8, 2] },

pond: { position: [-12, 0, -5], size: [27, 0.6, 18] },

bridge: { position: [-12, 1.2, -5], size: [4, 2.4, 22], rotationY: 0 },

mainHall: { position: [5, 0, 25], size: [24, 13, 17], rotationY: 0 },

pagoda: { position: [-27, 0, 22], size: [11, 29, 11], rotationY: 0.18 },

};

export const cameraAnchors = {

arrival: [0, 2.1, -43],

bridge: [-12, 3.0, -16],

finale: [22, 8.0, 42],

};

```

這不是建築設計圖，而是可版本控制的空間合約。建議明確記錄座標系與方位慣例；不同 3D 專案對北向、camera forward、Euler rotation 的假設不同，這正是 agent 最容易悄悄寫錯的地方。

後續交付順序：不要讓 AI 一次生完 70 秒

場景平面圖驗收後，依序拆成小型、可視化的交付物：

  • **Blockout**：只用方盒、圓柱、平面做主殿、塔、橋、池；渲染一張正交鳥瞰圖與四個地面視角，驗收比例和間距。
  • **程序化資產**：把屋簷、柱列、塔層、橋拱、蓮葉和石材拆成獨立 generator；每個 generator 都只接受 layout 的局部資料與 seed。
  • **材質與氣氛**：不用圖片貼圖也能使用 vertex color、noise、instancing、shader 與幾何細節；先以低解析度預覽，避免 shader 和陰影過早成為效能瓶頸。
  • **光照**：以固定太陽方位／高度產生 directional light、天空色與霧；用固定曝光檢查剪影、池面反射與屋簷暗部。
  • **分鏡與鏡頭**：將 70 秒切成 5–8 段，每段寫明時間、起終點、look-at target、焦段／FOV、速度曲線與驗收畫格。
  • **離線輸出**：用固定 fps、解析度與 deterministic seed 逐格渲染，再以 FFmpeg 編碼；不要用 `requestAnimationFrame` 的即時畫面直接當成最終影片證據。

純程式生成的效能護欄

「不准用模型和貼圖」不代表可以無限加幾何。應事先設置：

  • 近景／中景／遠景的三種細節層級；
  • 植被、屋瓦、蓮葉使用 `InstancedMesh`，不要各自建立 mesh；
  • 影子只保留敘事需要的主要物件，設定 shadow map 尺寸預算；
  • 噪聲與水面 shader 有 quality tiers，讓預覽和離線輸出使用不同設定；
  • 由 layout seed 和資產 seed 決定隨機結果，確保同一鏡頭可重現。

最後，日式寺廟只是視覺題材而非歷史保證。若要聲稱復原某座真實建築、儀式或文化元素，必須另行查證資料；在沒有研究來源時，較誠實的描述是「受日式寺廟建築語彙啟發的原創程序化場景」。
