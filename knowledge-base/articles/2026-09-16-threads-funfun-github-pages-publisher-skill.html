Threads｜GitHub Pages Publisher Skill：把靜態教材從本機變成可分享網址

一句話摘要

這個 Skill 把「GitHub、repository、push、Pages」的部署細節收在 agent 工作流裡，讓老師與一般使用者把已完成的靜態網頁安全發布成公開網址；它降低的是操作門檻，不會改變 GitHub Pages 的公開性與靜態網站限制。

社群分享的使用情境

方方老師指出，許多人已能以 AI 製作教學遊戲、互動教材、抽籤工具或班級網頁，卻卡在如何真正上線。分享的 `github-pages-publisher` 主打交出網站後說「幫我把這個網站上線」；更新時說「幫我更新網站」，由 agent 完成檢查、上傳、發布並回傳網址。

程式碼可確認的流程

公開 README 與 SKILL.md 顯示，版本 0.1.0 優先支援純 HTML/CSS/JavaScript、已產出的 `dist/`／`build/`，以及可標準 `npm run build` 的 Vite／React 靜態網站。發布前會檢查：

  • `index.html`、靜態發布可行性與是否需要 build。
  • `.env`、API key、token、private key 等可能外洩的敏感資訊。
  • Express、Flask、Django、PHP 等需要常駐後端的情況。
  • GitHub Project Pages 的絕對路徑、SPA 重新整理 404 風險。
  • GitHub CLI (`gh`) 登入狀態與 GitHub Pages 是否真的建立。

它採暫存 staging repository，只複製可發布內容後建立／更新 Pages repository，設計上避免直接重設或改寫使用者原始專案的 Git 歷史。發布後在原專案建立 `.github-pages-publisher.json` 記錄 owner、repository、網址與 branch，且宣稱不保存 token、不發布該檔。

使用前的界線

  • GitHub Pages 是公開靜態託管：不要放學生個資、內部文件、帳密、私密資料或真正的 API secret。
  • 需要 Node/Python/PHP server、資料庫私密憑證、SSR／Server Actions 的專案不能直接照此方式發布。
  • 前端 SDK 能運作不代表設定安全；尤其 Firebase、第三方 API 或 OAuth 設定仍應逐項檢視。
  • 第一次仍需在瀏覽器完成 GitHub 登入授權。Skill 可代替 Git 指令，但不能代替帳號權限與公開資料的責任。

對教學現場的實作建議

  • 先用不含個資的單頁教材或小測驗測試完整上線流程。
  • 發布前把 API key 改為後端代理、受限公開 key 或移除；不可將私密 token 置入瀏覽器檔案。
  • 用子目錄網址實測圖片、CSS、JavaScript 與重新整理子頁，確認沒有絕對路徑／SPA 404。
  • 建立「預覽 → 教師確認 → 公開發布」的流程；對學生作品採專案級隔離與明確公開同意。
