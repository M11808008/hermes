第一方資料：Buzz 實際是什麼？

Block 的 [GitHub repository](https://github.com/block/buzz) 將 Buzz 定義為「人與 agent 在同一個 room 裡共同建造」的自架工作區。其 README 可直接確認：

  • 每個 workspace／community 由 URL 指向；在目前單 relay 設定中，relay URL 對應一個 community。
  • 訊息、反應、workflow step、review approval 與 Git event 都以 Nostr 的簽章事件記錄；人與 process 使用相同事件模型，但擁有不同 keypair／身份。
  • README 列出的 agent 可做能力包含：開啟 repo、送出 patch、review code、執行 workflow、編輯 canvas、協調其他 agent、建立 channel 等。這是平台提供的互動面，不代表任一 agent 已獲得必要的外部帳號、工具、網路或部署權限。
  • 專案標示 Apache-2.0 授權；導入時仍須以當前 repository 的 LICENSE 與版本為準。

Hostinger 的角色：提供一鍵自架的 VPS 容器環境

Hostinger 的 [Buzz 應用頁](https://www.hostinger.com/applications/buzz) 把它定位為「可自架的 Nostr communication platform」，並提供預先設定的一鍵部署。該頁所述部署組合包括 Buzz relay、PostgreSQL（事件與全文搜尋）、Redis（即時 pub/sub）與 MinIO（Blossom 媒體儲存）。

這代表它降低了啟動基礎設施的摩擦，但仍需自行負責：

  • 選擇與維護 VPS 地區、費用、備份與更新節奏。
  • 管理 Nostr keypair、加入者身份、channel 成員與 agent 可做的動作。
  • 設定模型供應商金鑰、外部工具帳號、CI/CD 與 Git 權限；它們不會因安裝 Buzz 而自動安全地存在。
  • 對所有會寫入、寄送、發佈、刪除、付款或部署的 agent 動作加上人工核准與可回復措施。

頁面上的促銷價格、折扣、方案規格與續約條款均可能隨地區、期限與時間變動，應在付款前以 Hostinger 結帳頁與官方條款為準。

把「三個 AI 員工」落成可驗收流程

如果要測試影片的工作模式，建議不要一開始就交給 agent 自主交接，而應以小型、可回復的工作流驗證：

  • **角色分工明文化**：例如研究 agent 只蒐集可引用來源、執行 agent 只產出草稿、審核 agent 只檢查規格與風險；每個角色都有禁止事項。
  • **交接物固定化**：使用 ticket、輸入資料版本、輸出摘要、來源 URL、待決問題與下一步，不以聊天室口語當唯一規格。
  • **身份與權限分離**：每個 agent 用獨立 key／帳號及最小權限，不共用長效 token、個人 Cookie 或 production root 權限。
  • **將核准點放在風險行動前**：agent 可以提出 patch、訊息草稿或部署計畫；合併、寄送、付款、發佈與刪除由人確認。
  • **用結果而非角色數量衡量**：先驗證「可重現地完成一個低風險任務、來源可追溯、失敗能回復」，再擴大自動化。
