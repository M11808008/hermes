來源：AI郵報的深度整理；主要事實已交叉核對 Anthropic 官方公告〈Projects redesigned: from folder to conversation〉（2026-09-17）。

Claude Projects 從資料夾變成「對話式協調器」：工程工作流的真正改變

Anthropic 將 Claude Projects 重新設計為目標導向的長時程工作空間。它不再只是放置檔案、指令與對話的資料夾，而是由一個 project chat 擔任 **Coordinator（協調器）**，依目標安排多個雲端 Claude Code sessions（**Threads**）並行執行、追蹤與整合工作。

這項能力的重點不只是「同時開多個 agent」，而是把原本由人類承擔的任務切分、上下文交接、進度追問與成果回收，放入一個可持續管理的專案層。

一分鐘看懂

  • **輸入從指令變成目標**：指定專案目標、repo 或脈絡後，Claude 會先建議可立即展開的工作。
  • **Coordinator 負責調度**：主對話可規劃、派工、改變優先序、追問進度；可視為技術幕僚長，而不是又一個 coding chat。
  • **Threads 負責交付**：每個 thread 是獨立的 Claude Code cloud session，有自己的 repo 副本與 Git branch，可修改程式、跑測試、開 PR。
  • **跨 repo 可平行推進**：官方示例包括 API、Web、Mobile 三個 repo 同步遷移 deprecated endpoint；各 thread 提 PR 後，系統說明建議的合併次序。
  • **共享記憶與產物庫**：threads 會讀寫 project shared memory，並把檔案與產出收進 library，降低重複交代背景的成本。
  • **人仍須處理衝突與決策**：兩個 threads 改到同一段程式碼時，依然是正常 Git merge conflict，不會被黑箱自動覆蓋。

官方已確認的運作方式

1. Coordinator：對話式專案控制面

使用者可以在專案主對話中交辦完整目標，例如「把 checkout 的 p75 latency 降低」。Claude 可將 endpoint profiling、效能優化測試與 PR 建立，分派到平行 threads；使用者也可從手機查看、引導或調整工作。

官方用語是：使用者像向 chief of staff briefing 一樣說明需求，Claude 將工作路由到既有或新的 threads。這代表主對話專注在範圍、優先順序、決策與驗收，而非親自執行每項程式修改。

2. Threads：隔離的雲端 Claude Code 工作單元

每個 thread 是一個雲端 Claude Code session，擁有自己的 branch 與 repo copy。它可在連接的 repository 中執行測試、開啟 pull request；大型任務也可在 thread 內再使用 subagents、loops 與 workflows 拆解。

這能明顯改善傳統多 chat 的「stitching tax」：人類不用手動把 A 對話的結果搬到 B 對話、再人工拼接。不過隔離不等於完全免整合；凡是修改重疊，仍要以 PR review、測試與 merge conflict 流程處理。

3. 動態共享記憶：降低上下文重工

官方說明每個 thread 都會對 shared memory 有所貢獻並從中取用。例如系統能記住發布日改到週五、取消 export 功能的原因，或修改 billing service 前需先找誰確認。專案也會累積使用者偏好的更新頻率、是否積極啟動新 threads、回報詳細度等工作風格。

這是它與傳統「上傳文件＋固定 custom instructions」專案資料夾最實質的差別：context 不只被儲存，而會隨執行中的決策演進。

適合的實戰場景

  • **跨 repo 遷移**：同時改 API、Web、Mobile；讓 repo threads 各自完成 PR，再由人類依相依關係合併。
  • **效能／可靠度計畫**：例如把 checkout p75 latency 降低，讓不同 threads 分析 endpoint、執行實驗、提交可比較的結果。
  • **長時程研究或文件任務**：以同一專案記住來源、決策與產物，避免在每次對話重新 briefing。
  • **有明確驗收標準的多工作流任務**：需求切片相對獨立，但仍需要共同的目標、規範與人類 review。

重要限制與治理提醒

  • **目前是 Beta，且採分批開放**：官方公告當時先提供給部分使用 Claude Code cloud sessions 的 Claude Pro／Max 訂閱者；之後才逐步擴展。Web、Desktop、Cowork、Team、Enterprise 仍屬後續範圍，不能解讀成所有 Claude Projects 已全面可用。
  • **使用額度可能更快耗盡**：同時跑多個完整 Claude Code sessions，官方明確提示 project usage limits 可能更快到達；應監控 project-specific usage，並分別設定 coordinator 與 worker 的模型、effort level。
  • **雲端 thread 尚未等於本機／內網 agent**：公告時 threads 在 cloud 運作；官方稱與本機工具、程式碼及內網並行的能力「即將推出」。有機敏 code、私有網段或受管制資料時，先釐清資料流、connector 權限與合規邊界。
  • **共享記憶需要治理**：把專案決策、帳務服務聯絡人、發布資訊寫入 shared memory 很方便，也提高過期資訊、錯誤假設或敏感資訊被後續 thread 取用的風險。建議建立可編輯的決策紀錄、資料分類與定期 review。
  • **PR 不是自動上線授權**：保留 CI、code review、branch protection、secrets scanning 與 production approval。agent 能開 PR，不代表應自動 merge 或 deploy。

對欒帥的實作建議：先做「小型可觀測 agent program」

將它用在可拆分、可驗收、低到中風險的工作，例如「網站三個不相依頁面的內容／測試／效能整理」，而不是一開始交給它整個關鍵系統重構。每個 project 建議先寫清楚：

  • 目標與成功指標（例如 latency、coverage、轉換率，而不只是「改善」）
  • repo／資料範圍與不可碰觸的區域
  • 每個 thread 的權限、預算與停止條件
  • PR review owner 與 merge／部署責任人
  • shared memory 可記錄與禁止記錄的資訊

成熟的用法是：**人類維持目標、邊界與最終問責；Coordinator 負責編排；Threads 在可觀測且可逆的範圍內加速執行。**

可直接採用的英文指令框架

You are the project coordinator. Our goal is to reduce checkout p75 latency by 25% without changing payment behavior.

First, propose a scoped plan and success metrics. Then create independent threads only where work can be safely parallelized.

Each thread must: work on its own branch, run relevant tests, document assumptions and risks, and open a PR rather than merge.

Do not modify payment authorization, production configuration, secrets, or customer data flows. Report dependencies, conflicts, and recommended PR merge order in the main project chat.
