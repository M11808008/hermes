Will 保哥｜Codex app 設定 Luna Max：用較低成本接近 Sol Medium 的 coding agent workflow

來源是 Will 保哥的技術交流中心 Facebook 公開貼文。貼文主張：在 Codex app 中，`GPT-5.6 Luna (max)` 的智力表現可接近 `GPT-5.6 Sol (medium)`，但價差約 25 倍；若使用者會設定 reasoning effort / model controls，Pro 5x 訂閱會更不容易耗盡，Plus 訂閱也能更順暢使用。

一句話摘要

這則貼文值得收錄，因為它把 Codex / ChatGPT coding agent 的「模型選擇」從單純追最高階模型，轉成「模型 × reasoning effort × speed × token 成本」的工作流最佳化問題：日常開發不一定都要用 Sol，中低成本模型搭配 Max reasoning 可能更適合高頻迭代。

貼文重點

  • 作者建議到 Codex app 的 Settings 開啟或調整 reasoning effort，尤其是預設停用的 `Max`。
  • 對日常開發任務，可嘗試改用 `GPT-5.6 Luna (max)`。
  • 作者稱 Luna Max 的能力約等於 Sol Medium，但價格/用量成本差距約 25 倍。
  • 這種設定能讓 Pro 5x 或 Plus 訂閱者更省 token / 用量，作者稱之為「Token 財富自由」。
  • 貼文 hashtag：`#Token_Independence_Retire_Early (T.I.R.E.)`

留言區補充觀察

可見留言提醒了幾個 trade-off：

  • 有讀者確認理解為「Luna + Max + Fast」可能取得更多用量，同時接近 Sol Medium 的能力。
  • 也有人指出 Luna Max 與 Sol Medium 的 token 使用量、速度仍有 trade-off，Sol Medium 可能更省 token 或更快。
  • 多位留言提到 Max 可能較慢，Fast 需要開啟。
  • 有人詢問 CLI 是否能設定，代表這個設定不只影響 GUI app，也可能延伸到 Codex CLI / agent workflow 的模型控制議題。

與既有 AI 學習雷達脈絡的連結

AI 學習雷達已收錄多篇 GPT-5.6 / Codex / Luna / Sol 相關條目，包括：

  • ChatGPT APP / Codex 改版：Sol、Terra、Luna、Sites、Remote Control 的工作平台化。
  • 透過 CLIProxyAPI 讓 Claude Code 使用 GPT-5.6 Sol 的 Claudex 工作流。
  • Codex Sol 主代理 + Luna Worker 子代理的 subagent 派工流程。

這則貼文補上另一個重要角度：不是只討論「哪個模型最強」，而是把模型分層用在不同任務密度與成本結構上。

欒帥可用的實務框架

  • 高風險 / 最終整合：保留 Sol / high-tier model。
  • 日常 coding iteration：嘗試 Luna + Max reasoning，降低用量消耗。
  • 子代理 / worker 任務：把可拆、可驗證、可重跑的任務交給較便宜模型。
  • 速度需求高時：同時檢查 Fast / reasoning effort 的組合，而不是只看模型名稱。
  • 用量管理：把「模型能力」與「token 成本、速度、訂閱額度」一起納入 workflow 設計。

Caveats

  • 這是 Facebook 社群貼文觀察，不是 OpenAI 官方 pricing / benchmark 文件。
  • `GPT-5.6 Luna`、`Sol`、`reasoning effort`、`Fast` 等名稱與介面可能隨 Codex app 更新而變動。
  • 「智力等同」與「25 倍價差」屬作者使用經驗 / 社群說法；真正任務表現仍需依專案、提示、上下文長度、工具使用與驗證方式測試。
  • Max reasoning 可能提高推理時間或 token 使用，留言區也提到速度與用量 trade-off。

Why it matters

AI coding agent 的成本最佳化正在變成一門實務技能。未來不會是永遠選最大模型，而是像雲端運算一樣，針對任務選擇不同規格：主代理用高階模型判斷與整合，worker 用較低成本模型大量執行，並以測試與審查補上可靠性。這則貼文是 Codex app 使用者開始形成「模型調度 / 成本工程」意識的代表案例。
