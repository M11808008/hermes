Threads｜Moco Lee：Claude + Odoo + Zeabur 組出低成本 AI ERP 中台的實作流程與風險邊界

來源是 Moco Lee（@mocoo.lee）在 Threads 分享的一串實作心得：用 Claude 協助部署與串接 Odoo，把開源 ERP 當成公司中台，再用 Claude 讀訂單、報價、採購、盤點等資料並更新系統。這則貼文的價值在於把「AI Agent + 現成 ERP」當作比從零刻系統更務實的路徑；同時也需要清楚標註 ERP、財務、庫存與權限的風險邊界。

公開 Threads 內容

Threads 可見 canonical URL 為 `https://www.threads.com/@mocoo.lee/post/DbKb2rpmvHH`，頁面擷取時主串顯示約 3,704 次瀏覽。作者分享的流程大致如下：

  • 先用 Zeabur 伺服器安裝 Odoo。作者認為 Zeabur 的 AI 支援程度高，安裝 Zeabur skill 給 Claude 後，可以讓 AI 協助開伺服器與專案。
  • 讓 Zeabur 安裝 Odoo 社區版模板。作者描述過程中只要同意資料 / 權限，安裝就能完成。
  • 串 Odoo 網址。作者建議公司或實驗專案都應該有自己的網址，並推薦 Cloudflare 作為便宜網域管理選項。
  • 串 Odoo 與 Claude。作者表示自己教 Claude 寫 API 或使用 Odoo 本身 API，讓兩個工具串起來。
  • 導入資料。作者讓 Claude 將公司資料、產品資料、採購單、報價單等打入 Odoo。
  • 加入自訂頁面。作者讓 Claude 做一個統整總覽頁，抓 Odoo 數據做 dashboard。

貼文留言中有人問：「你們生出來的財務資料有經過會計師到場查帳和審核嗎？」作者回覆：「自己管理用的。」這點很重要：本篇歸檔將它定位為「內部管理 / 原型 / 個人公司中台實驗」，不是已通過財務、稅務或審計合規的 ERP 導入案例。

官方來源與查核

Odoo 方面，Odoo 官方版本比較頁確認 Odoo 分為 Community（open-source）與 Enterprise（licensed）兩個版本；Odoo GitHub 與官方 license 文件也確認 Odoo Community Edition 以 LGPLv3 授權發布。這支持貼文對「開源社區版 / 線上付費版本」的基本描述，但「免費版閹割一些功能、仍堪用」屬作者與常見導入經驗的概括，實際功能差異仍需依 Odoo 當前版本與模組確認。

Odoo API 方面，Odoo 官方文件提供 External RPC / External API 文件，說明可透過外部 API 存取與操作 Odoo 資料。這支持「讓 Claude 寫 API 或用 Odoo 本身 API 串接」的可行方向。不過 Odoo 19 文件也提醒既有 XML-RPC / JSON-RPC 端點有未來移除時程，新的導入應追蹤官方最新版 API 路線。

Zeabur 方面，Zeabur 官方模板頁提供 Odoo Deploy Guide，可一鍵部署 Odoo；Zeabur templates 文件也說明模板部署會建立服務並串接設定。Zeabur 的 Claude Code Skills 官方文件則明確把 Zeabur plugin 定位為將自然語言轉為 infrastructure operations，可部署服務、租伺服器與管理設定。這支持貼文中「把 Zeabur skill 裝給 Claude，讓 AI 管伺服器 / 開專案 / 安裝 Odoo」的核心方向。

Cloudflare 方面，Cloudflare Registrar 官方頁與 docs 表示 Cloudflare Registrar 以 at-cost domain registration / renewal 為定位，沒有加價費用。這支持作者對 Cloudflare 網域成本相對低的判讀；但實際 `.com` 價格、稅費與地區付款條件仍需以 Cloudflare 當下 checkout 為準。

實務判讀

這則貼文值得歸檔，因為它示範了一條比「從零 vibe coding ERP」更安全、也更快驗證價值的路徑：不要讓 AI 從空白專案重造 ERP，而是讓 AI 圍繞成熟的 Odoo schema、模組、API、權限與資料模型工作。這能把 AI Agent 放在「部署、串 API、導資料、做 dashboard、批次更新」這些輔助層，而不是直接承擔整套 ERP 的制度設計責任。

對小公司或個人事業來說，這個架構的吸引力是：

  • Odoo 提供既有 ERP / CRM / inventory / accounting 等資料結構與流程；
  • Zeabur 降低部署與 DevOps 門檻；
  • Claude / agent skills 降低寫 API、設定環境、導入資料與做 dashboard 的摩擦；
  • Cloudflare 讓測試專案可以快速有正式網址與 DNS 管理；
  • 老闆可以先把 ERP 當「內部管理中台」驗證流程，而不是一開始就買昂貴套裝系統。

但真正的風險也正好在這裡：ERP 不是只有頁面與資料表，還包含權限、審核、對帳、稅務、資安、備份、異常處理、audit trail、資料歸屬與責任邊界。AI 可以加速部署與串接，但不能自動替代會計師、ERP 顧問、資安審查或內控制度。

建議導入邊界

若要把這則流程變成可落地的公司實驗，建議先限縮範圍：

  • 第一階段只做非正式的內部管理資料，不直接作為報稅、法定帳冊或對外承諾依據。
  • 先導入假資料或低風險資料，確認 Odoo 權限、備份、還原、API token、DNS 與 HTTPS 都正常。
  • Claude / agent 只拿最小權限的 API token；能寫入哪些 Odoo model 要明確列白名單。
  • 所有訂單、報價、採購、庫存寫入都要保留 audit trail 與人工審核流程。
  • 涉及財務資料、發票、稅務、薪資與個資時，需要會計 / 法遵 / 資安角色介入，而不是「讓 AI 自己解決」。
  • 若要正式營運，需規劃資料庫備份、權限分層、異常告警、版本升級、rollback 與災難復原。

補充邊界

  • 貼文是作者個人實作分享；部署成本、Zeabur 價格、Claude 方案、skill 能力與 Odoo 模板狀態都可能變動。
  • Odoo Community 與 Enterprise 功能差異會隨版本調整；是否能滿足會計、庫存、採購與在地法規需求，要逐模組評估。
  • AI 自動導資料若沒有 schema 驗證與人工抽查，可能產生錯欄位、重複資料、漏單或金額錯誤。
  • ERP 牽涉公司核心資料；即使只是「自己管理用」，也應先做權限、備份、日誌與資料外洩風險控管。
