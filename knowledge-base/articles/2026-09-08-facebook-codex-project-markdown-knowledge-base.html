Facebook｜Codex 中文社群：把專案規則整理成 Markdown，讓 AI 不必每次從零開始

一句話摘要

把「每次都要重新交代的工作規則」寫成一份經過確認的 Markdown，放進專案資料來源，讓 AI 更容易沿用同一套方法；但仍要做來源、版本與實際讀取結果的驗收。

貼文重點

貼文作者原本以為 ChatGPT Project 只是把聊天與檔案放在同一個資料夾，後來發現真正有差的是：是否把常用規則整理起來。

適合寫入 MD 的內容包括：

  • 專案目標
  • 資料來源
  • 工作流程
  • 重要限制
  • 輸出格式
  • 驗收標準

這樣做的好處，是把一次對話中的經驗轉成下次仍能使用的工作規範，降低每次重新說明「先看來源、不要亂猜、照流程做、最後要檢查」的成本。

不要把 Markdown 當成魔法記憶

這篇貼文最值得保留的提醒，是「上傳不代表永遠記得，也不代表資料一定正確」。實務上仍應確認：

  • AI 是否真的讀到該檔案。
  • 文件版本是否為最新。
  • 規則是否互相矛盾。
  • 最終輸出是否符合驗收標準。

因此，較穩定的分工是：聊天負責探索，Markdown 負責留下經過確認、下次還能用的規則。

可直接套用的 MD 骨架

```md

專案名稱

專案目標

  • 要解決什麼問題

可信資料來源

  • 官方文件：
  • 內部資料：
  • 不可使用的來源：

工作流程

  • 先做什麼
  • 如何交叉確認
  • 何時需要詢問

重要限制

  • 不可猜測的內容：
  • 隱私與權限：

輸出格式

  • 語言：
  • 欄位：
  • 連結與引用：

驗收標準

  • [ ] 來源已核對
  • [ ] 版本已確認
  • [ ] 結果符合格式

```

判讀與延伸

這則貼文與 AI agent、Codex、ChatGPT Project 及個人知識庫的共同核心，是把「提示詞技巧」提升成「可版本控管的作業規格」。若規則會長期使用，建議放在 Git 管理的 Markdown 知識庫，而不是只留在某一次聊天裡。

本則貼文未提供特定工具文件或程式碼專案；本文保留的是作者的工作方法與實務提醒，不把個人經驗延伸宣稱為 ChatGPT 的官方保證。
