Hermes Agent 的官方功能與設定確實覆蓋這四類主題：

  • 上下文：context compression、skills、memory、session、project context。
  • 子 Agent：`delegate_task`、多 agent 任務拆分、隔離上下文與工具集。
  • 成本：provider / model 切換、credential pools、prompt caching、compression、toolset 控制。
  • 工作流：cron jobs、webhooks、gateway、多平台訊息入口、Kanban、profiles。

可驗證的「四組設定」解讀

### 1. 上下文：避免長文件只讀一半

截圖字幕點出一個實務痛點：「讀長文件只讀到一半」。在 Hermes 裡，這通常不是單一開關能解，而是上下文策略：

  • 用 skill 保存可重複工作流，避免每次把長規則重新塞進 prompt。
  • 用 memory 保存長期偏好與穩定事實，但不要塞短期任務紀錄。
  • 長文件要先分段擷取、摘要，再把必要段落回填，而不是一次塞滿 context。
  • 遇到大型任務時，讓子 Agent 分工讀不同檔案或不同來源，主 Agent 只接收摘要。
  • 對專案任務，可利用 workdir / 專案上下文檔案，讓 agent 自動讀取必要規範。

對欒帥的知識庫工作流來說，這也是為什麼「文章、source archive、圖片、部署驗證」要拆成穩定流程，而不是每次靠臨場 prompt。

### 2. 子 Agent：把任務拆出去，保留主線清晰

Hermes 的 `delegate_task` 可以派出隔離上下文的子 Agent。它適合：

  • 平行查核多個來源。
  • 讓一個子 Agent 做 code review，另一個整理文件。
  • 在不污染主對話上下文的情況下探索大型 repo。
  • 把背景資料蒐集與最終決策分離。

這類設計的重點不是「開越多 agent 越好」，而是讓主 Agent 保持決策與整合，子 Agent 負責可隔離、可驗收的子任務。

### 3. 成本：把模型、工具與上下文一起控管

Hermes 的成本優化不只靠換便宜模型，而是幾個層次一起做：

  • 根據任務切換 provider / model。
  • 限制不需要的 toolsets，減少工具 schema 與上下文負擔。
  • 用 compression 與摘要降低長會話成本。
  • 用 skills / memory 避免重複解釋相同背景。
  • 將固定檢查改成 cron script-only watchdog，需要推理時才叫 LLM。

對日常使用者來說，最有感的是：把「查資料、讀檔、部署驗證」交給工具，把「判讀與摘要」留給模型。

第二張截圖補到一個很具體的成本提醒：後台任務與 auxiliary 任務的模型路由，會直接影響 token 帳單。畫面中可見 `auxiliary.vision.provider: auto`、`model: ''` 等設定，字幕則說「Auto 跟隨主模型，不會自動選擇最便宜的模型」。

這個提醒很實用：`auto` 應理解為「沿用或自動接上目前可用的模型後端」，不是「自動幫你用最低價模型」。如果主模型選得昂貴，視覺、網頁抽取、壓縮或其他後台任務也可能被帶到相同成本層級。比較穩的做法是：

  • 對 vision、web_extract、compression 等 auxiliary 任務明確指定便宜且足夠的 provider / model。
  • 高推理任務用強模型；批次擷取、格式轉換、健康檢查用便宜模型或 script-only。
  • 定期用 Hermes 的 usage / provider 帳單介面回查成本，不要只看單次聊天體感。
  • 若任務只是固定檢查或部署驗證，優先用工具與腳本完成，避免把低價值步驟交給高價模型推理。

### 4. 工作流：從聊天變成可持續執行的系統

Hermes 的工作流能力包括 cron、webhooks、gateway、profiles、kanban、sessions 等。這讓它可以從「你問我答」變成：

  • 固定時間產出摘要或巡檢。
  • 收到 LINE / Telegram / webhook 後自動處理。
  • 針對不同用途建立 profile，隔離記憶與工具設定。
  • 將大型任務切成可追蹤的 kanban 工作項。
  • 將重複成功的做法沉澱成 skill。

這也是 Hermes Agent 在教學與個人知識管理上有價值的原因：它能把「一次性的 AI 幫忙」變成「可維護的 AI 工作流」。
